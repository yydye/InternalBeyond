## 1 · 真实 tool execution graph（Phase 0 只读审计）

```
用户回合
├─ callApiChatStream / callApiChat        ← provider 循环（两条路径，各自 4~5 处 `continue`）
│    ├─ IBFC.prepare()                     探测系统提示里的工具块 → 构建 tools
│    └─ for(round;;)                       每轮 = provider → tool → provider
│         ├─ ① _callApiChatStreamOnce / Once            【调 provider】
│         │     ├─ 流式：feedAnthropic/feedOpenAI → takeCalls
│         │     └─ 非流式：extractFromResponse → _nsCalls
│         ├─ ② IBFC.runRound()                          【唯一执行工具的地方】
│         │     ├─ MCP   → IBMCP.execOp(name,args)      本地工具？→ IBFC.execLocalTool
│         │     │    ├─ mcp.*    → IBMCP.call() → MCP 服务器（JSON-RPC）
│         │     │    ├─ bridge.* → IBNET.execOp() → WebSocket RPC（90s 超时）
│         │     │    └─ 其他      → _ibToolFetch() → 本地 webhook（15s 超时）
│         │     ├─ ctx.ledger[key] = r                  台账（**只用于渲染回查**）
│         │     └─ emit(<ws_tool fc="1">) → site-operations._ibExecToolOp → ledgerGetByOp
│         │                                            （fc=1 分支：不执行、不再排队注入）
│         └─ ③ `continue` 回到 ①                        【继续下一轮】
└─ XML 通道：_parseWsOps → _execWsOps → _ibExecToolOp   同一个执行器，另一条入口
     └─ _wsToolContinue → callApiChat（非流式）→ 递归续轮
```

审计结论（实测，非阅读印象）：

| 现象                         | 位置                                                         | 后果                                    |
| ---------------------------- | ------------------------------------------------------------ | --------------------------------------- |
| `continue` 绕过 `maxRounds`  | `callApiChatStream:4114` / `callApiChat:4272`                | 轮检查写在循环体后段，`continue` 到不了 |
| `maxRounds` 实际只管外部工具 | `roundLocal` 只在 `calls.some(!isMcp)` 时自增                | **纯 MCP 回合一轮都不计**               |
| 台账不做去重                 | `ctx.ledger[ledgerKey(...)] = r` 只写不判                    | 同 `{name,args}` 可无限重复执行         |
| 失败可立即无限重试           | `runRound` 无失败计数                                        | —                                       |
| 只有单工具超时               | `_ibToolFetch` 15s / `IBNET.callTool` 90s                    | 无"工具周期"总时限                      |
| 三套互不相干的"轮次"         | `ib_fcRounds` / `servers[].maxRounds` / `_WS_TOOL_CONT_MAX`  | 没有一套是"总预算"                      |
| 工具执行器                   | 生产只有 **1 个**（`IBMCP.execOp` 被 `commerce-adapter.js` 包了一层观测） | 不存在多执行器                          |

## 2 · canonical fingerprint

```
fingerprint(toolName,args) = sha256( json(toolName) + "|" + stableSerialize(args) )
```

- 对象键排序 → `{a:1,b:2}` ≡ `{b:2,a:1}`；显式 `undefined` 键被丢弃；**数组顺序保留**（顺序是语义）。
- 不含 tool-call id、UI 文本、时间戳、顺序号。
- 循环引用 → 稳定哨兵，不抛不爆栈。
- **纯 JS SHA-256**（约 40 行），与 `node:crypto` 逐字节一致（D7 用 node:crypto 交叉验证，含中文与代理对）—— 这一条是开发中真实抓出来的：原先 Node 走 `node:crypto`、浏览器退化到 FNV，**同一调用两端指纹不同**，"canonical"就不成立。
- 观测面只出现 16 字符前缀；敏感键（`apiKey/authorization/token/secret/password/...`）在调试载荷里替换为 `[redacted:长度]`。

## 3 · budget policy

| 额度                        | 默认                                    | 语义                                                         |
| --------------------------- | --------------------------------------- | ------------------------------------------------------------ |
| `maxRounds`                 | 5（用户设置 `ib_fcRounds`，夹到 1..64） | provider→tool→provider 的**总轮次**                          |
| `maxToolCalls`              | 16                                      | 单回合工具**执行次数**（与轮次不是同一个量）                 |
| `maxRetriesPerCall`         | 2                                       | 同一失败调用的重试次数（首次不计）                           |
| `successRepeatLimit`        | 2                                       | 成功调用在同回合被再次调用的上限                             |
| `duplicateConsecutiveLimit` | 2                                       | 完全相同调用**连续**出现几次即熔断                           |
| `maxCycleMs`                | 120000                                  | 整个工具周期的墙钟上限                                       |
| `toolCallTimeoutMs`         | 60000                                   | 单次调用的**软截止**（只停止等待，不中断已发出的请求，不改工具语义） |

有限性是构造性的：`Infinity/NaN/负数/垃圾值` 一律回落默认，`maxAttempts` 类字段被强制夹紧，公开调用面**没有任何**清空计数/重置熔断/强制放行的入口（A7/A8 逐名断言）。派生不变量：`successRepeatLimit ≤ maxToolCalls`。

## 4 · duplicate policy（四类分开，不假装幂等）

| 类别                    | 判据                               | 额度                        | 理由                     |
| ----------------------- | ---------------------------------- | --------------------------- | ------------------------ |
| `new`                   | 本回合首次                         | 总工具预算                  | —                        |
| `duplicate-consecutive` | 连续同一个指纹，**上次成功**       | `duplicateConsecutiveLimit` | 模型卡住的最强信号       |
| `duplicate-repeat`      | 同指纹但中间夹了别的调用，上次成功 | `successRepeatLimit`        | 状态型工具的合法再问     |
| `retry`                 | 同指纹且**上次失败**               | `maxRetriesPerCall`         | 失败重试不该被"重复"掐死 |

## 5 · breaker reasons（封闭集合，trip 是终止事件）

`round-budget-exhausted` · `tool-budget-exhausted` · `duplicate-tool-call` · `duplicate-tool-call-consecutive` · `retry-budget-exhausted` · `tool-cycle-timeout` · `no-active-cycle`

没有"其它/未知"兜底值（E4 断言）—— 兜底会让静默 break 重新可能。熔断后：不再授权任何工具（含**同批中途**重新读取一次）、`runRound` 返回 `done:true`、回合不再向 provider 索要、原因写进用户可见输出流与 trace，**不伪造模型回复**。

# P11-3D.1 · XML Continuation Guard Compatibility（**已关闭**）

**决定性修正（方案 A）：周期的 owner 从"一次 `callApiChat*` 调用"上移为"宿主 AI turn"。**

## 11.5 · 冻结的核心定义

```
ONE HOST AI TURN
  = ONE TOOL EXECUTION CYCLE
  = ONE TOTAL BUDGET
```

`maxRounds` 的语义同时冻结为：**一个 HOST AI TURN 内 provider → tool → provider 的总轮次**，
不是"一次 `callApiChat()` 函数 invocation 的轮数"。XML continuation 递归进入
`callApiChat` **不得**重置 `maxRounds`；toolCalls / retry / duplicate / elapsed 语义不变。

### 被废弃的旧模型（不掩盖）

P11-3D 把周期开在 `callApiChat*` 内部：**"一次 callApi 调用 = 一个周期"**。
它不成立，两条实测理由：

1. XML 批次（宿主解析回复正文 → `_execWsOps`）与工具续轮（`_wsToolContinue`）
   都发生在 `callApiChatStream` **返回之后**，那一刻周期已被它的 `finally` 收掉 ——
   这条通道全程没有周期可问，四类预算（tool-count / duplicate / retry / elapsed）
   对它全部失效，执行也不入账（观测面 `toolCalls=0` 而工具真的跑了）；
2. 续轮内部又调 `callApiChat`，于是它自己**另开一个周期** —— 一个 turn 两个预算，
   轮次计数还被重置。

**这两条是本阶段用生产路径实测出来的（见 §12），不是推理。** 修正方式见 §13。

## 12 · 旧模型的真实生产时序（实测存档）

整个场景在**同一次 browser evaluate / 同一个真实 turn 内**驱动，承载必须是 HTTP
（`file://` 下权威整体失效）。被驱动的都是生产实现：`callApiChatStream`、
`_parseWsOps`、`_execWsOps`、`_ibExecToolOp`、`window._wsToolContinue`
（含其内部递归 `callApiChat`）；只有 provider 与工具 webhook 是 mock。

实测事件序列（当时版本）：

```
_toolCycleBegin(ctx)      ← callApiChatStream:4173   开 cycle 1，ctx._guard = g
_toolCycleEnd(ctx)        ← callApiChatStream:4233   cycle 1 **结束**，ctx._guard 清空
── turn 返回 ──
_execWsOps(...)           ← 宿主 XML 首轮批次：**此刻没有活动周期**
_wsToolContinue(round=1)  ← 内部 cycleBegin(null) → null（旧 _tg 恒 null 的来源）
   └ _toolCycleBegin(ctx) ← 续轮内部 callApiChat:4248  另开 cycle 2（**不是**外层的延续）
      _toolCycleEnd(ctx)  ← callApiChat:4301            cycle 2 结束
   └ 续轮 XML 批次        ← 同样落在周期之外
```

即：**工具周期的作用域 = 一次 `callApiChatStream` 调用链**，而 XML 批次与续轮都发生在
那一刻之后。因此 XML 通道不是"被熔断绕过"，而是**根本没有周期可问**。

## 13 · 原红灯是否 harness artifact：是，但真实缺陷更根本

- 旧红灯**确实是** harness artifact：两次 evaluate 之间周期已结束、且驱动器自己先
  `cycleBegin` 一次会把 `ctx._guardCycle` 翻成 `false`，使生产 finally 不再拥有周期。
- 修正 harness（单次 evaluate、不预先开周期、从 `cycleBegin` 探针捕获**真正的**
  owner ctx —— 即 `IBModelCore.prepare` 在 `callApiChatStream` 内部新建的那个，
  外部的 `IBFC.prepare` 返回的是另一个对象）之后，红灯**没有消失**，而是换成了
  一个真实的、更根本的失败点：周期作用域。
- 另有两个真实陷阱：guard 实例是 `Object.freeze` 的（在它上面挂计数器静默失败，
  读数恒 0 —— 足以把"接线正确"误读成"接线不存在"）；`_toolCycleBegin` /
  `_ibExecToolOp` 是 IIFE 私有的，页面全局无法重新绑定。

| 文件 | 改动 | 必要性 |

## 15 · XML 与 FC 是否真正共用 ONE TURN = ONE BUDGET：**否**

- 轮（round）**是**共用的：续轮经 `callApiChat` → `_roundBudgetAllows`。

- 续轮还会**另开一个 cycle**（第 2 个预算），而不是继承外层的那个。

## 17 · 上移后的所有权模型与传播图（Phase 1–3）

### host turn 边界

| 入口 | 是不是宿主回合 | cycle owner |
| --- | --- | --- |
| `sendChatMessage()` 单聊 | **是**（`try` 起点 → `_turnLc.end()`） | 是（`ownsCycle=true`） |
| `sendChatMessage()` 群聊 | **是**，但**每个发言成员各一个** | 是 |
| `_wsToolContinue` 内部递归 `callApiChat` | 否（继承） | 否 |
| XML 首轮批次 `_execWsOps` / 续轮批次 | 否（继承） | 否 |
| `callApiChat*`（无宿主，如诊断/设置向导/摘要） | 隐式回合（本调用即 owner） | 是 |
| 后台主动消息 / 摘要 / 活跃规划 | 各自的隐式回合（**不同实例**） | 是 |
| `regenerate` / `retry` | 同一个宿主入口 → 新 turn | 是 |

> 群聊按成员切分是有意的：群聊分支在一个函数里跑完所有发言成员，若整段只开一个
> 周期，"一次发言 = 一个 turn"就被破坏，后发言成员的额度会被前一个成员吃掉。

### guard 的显式传播（没有全局"当前回合"可猜）

```
宿主 turn (sendChatMessage)
  ├─ opts._ibTurn ──→ callApiChat*/callApiChatStream
  │                    └─ IBFC.prepare → ctx._ibTurn = turn（_ibBindTurn）
  │                       └─ _toolCycleBegin(ctx, turn) → IBFC.cycleBegin(ctx, meta, turn)
  │                          · ownsCycle=true 且无活动周期 → 新建实例 + startCycle
  │                          · 否则 → 绑定 turn.guard，**不开新周期**
  ├─ ictx._ibTurn/_guard ──→ _execWsOps ──→ _ibExecToolOp（authorize → execute → settle）
  ├─ o._ibTurn/_guard ──→ _wsToolContinue ──→ 递归 callApiChat（同一个 turn）
  └─ _turnLc.end() ──→ IBFC.cycleEnd(turn)（唯一收尾点，幂等）
```

**禁止项（已不存在的写法）**：全局 mutable guard、在 storage 里存活动周期、
按"当前唯一活动 cycle"推断 owner、XML 单独建第二个 guard。

### 周期实例的分配

`IBFC._newGuard()` 是**唯一分配点**：每个开周期的 turn 拿一个**刚创建**的实例
（策略在创建时从宿主设置读一次 → 可见设置仍是唯一事实源）。`IBFC._tdGuard` 退化为
"最近分配的那个"这一观测指针，**不再**充当所有权来源 —— 并发的前台/后台因此
不会互相累计、不会互相 end、不会互相 reset。

### 轮预算的归属（一条 canonical 口径）

| 位置 | 询问 |
| --- | --- |
| `callApiChat*` 循环顶部（`round>0`） | `beforeCall('__round__', null, {kind:'round'})`（在任何 `continue` 之前） |
| `runRound` 工具执行后 | `beforeRound()` / `afterRound()`（provider→tool→provider 记一轮） |
| `_wsToolContinue` 递归 | 同一个 guard 的同一份计数，不新建、不重置 |

## 22 · 本阶段顺带修掉的三个真缺陷（必须交代）

这三条都是**本阶段验收条件所依赖**的生产缺陷：不修它们，端到端无法成立。
因此计入本阶段，而不是"顺手改了别的 bug"。

1. **每一次流式单聊回合都在收尾处抛 TDZ 异常。**
   `streamRefs.forEach(ref=>{_mbAppendNoticeCard(..., aiMsg)});` 写在
   `const aiMsg = {...}` **之前**，于是每次流式回合都在这里抛
   `Cannot access 'aiMsg' before initialization`：消息不落库、`_sendResult.ok=false`、
   用户看到的是一条"请求失败"。它被 `catch` 吞掉，所以既不影响 provider 调用、
   也不影响已经完成的工具执行 —— 只让整个回合在收尾时失败。
   **这正是"宿主回合还没结束就已经失败"**，周期所有权必须和它一起修。
   修法：把那一行移到 `aiMsg` 落库之后（也就是它原本的语义位置）。

2. **尾部的【外部工具】块被截断掉 → 原生 FC 永远不激活。**
   `buildSiteContext` 里 `truncateContext(ctx, Math.max(2000, 8000 - wsBlock.length))`
   的意图是"给工作区指令预留位置"，但当 `wsBlock` 自身超过 8000 字符时那个下限
   2000 会让 `ctx` 被截到 2000，随后 `wsBlock` 被**逐字接在后面** —— 于是 `ctx`
   那 2000 字符比 `wsBlock` 还早结束，**尾部的外部工具块被整块截掉**。
   实测：真实宿主回合里 provider 收到的 `tools` 参数恒为空（工具开关看着是开的，
   一个工具都调不到），XML 通道成了唯一的实际路径。修法：工具块单独抽出、
   在截断**之后**追加（能力声明与长度预算分开）。

3. **`fc="1"` 的渲染卡片被当成第二次真实调用来授权。**
   原生 FC 执行完之后，宿主会把调用序列化成 `<ws_tool name=… fc="1">` 交给卡片渲染；
   `_ibExecToolOp` 此前对**所有** op 都走 `beforeCall`/`settleCall`，于是**一次真实
   执行在账本里记成两次**（`toolCalls=2` 而真实执行 1 次），去重/重试判定随之全部失真。
   修法：`fc="1"` 是回放（按台账填卡、不执行任何东西），授权与结算只对
   **真的要去执行**的调用生效。
