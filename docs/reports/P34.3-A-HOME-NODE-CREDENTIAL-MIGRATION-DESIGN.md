- 日期：2026-09-26
- 基线：`HEAD=85f91be` + 工作树；运行版 `%LOCALAPPDATA%\Programs\InternalBeyond`
- 性质：**STRICT DESIGN ONLY**。本阶段**未改**代码 / schema / Vault / 数据 / resolver / Installer / Recovery；未启动 Active/Re-arm；未 commit。
- 目标：设计 Home Node 从 **plaintext credential mirror** 到 **Vault authority** 的迁移。
- 状态：**DESIGN ONLY — 待评审后再进入 P34.3-B（受控实现）**

## 1. Goals / Non-goals

**Goals**
1. Home Node 运行时**不再持有明文 provider 凭据**（`character_runtime_specs.spec_json.apiKey`）。
2. Home Node 角色执行（LAN/mobile 回合 + 后台理解）改为**请求时经凭据解析器取运行时 secret**，与桌面同一 authority。
3. 保持 mobile-safe DTO 边界（spec 永不出站）与 `characters`/`character_runtime_specs` 分表不变。
4. 迁移**可回滚、可灰度、可验证**。

**Non-goals（本轮与非本轮）**
- 不把 `apiConfigs` authority 整体搬到 Node（原 M1-B 的 Strategy B，仍是另一阶段）。
- 不改 Vault schema / 加密 / `credential_*` 契约 / resolver allowlist 语义（仅在需要时**新增**可解析的绑定集合，见 §6.4）。
- 不引入 Credential V2。

## 2. Invariants（必须始终成立）

1. **单一 secret authority**：明文只活在运行时内存（请求作用域），持久层只有加密 Vault。
2. **DTO 边界**：`characters.dto_json` 只含 mobile-safe 字段；spec 永不进入任何 HTTP 响应 / 设备同步。
3. **最小权限**：任何凭据解析器只解析**明确允许**的 binding（沿用 P34.1 的 allowlist 思路）。
4. **fail-closed**：解析失败 → 明确报错（`CONFLICT` / 不可运行），**不**回落到明文、不静默降级。
5. **Recovery/重建边界**：`character_runtime_specs` 保持 `DEFER`（`composite-reconstruction-executor.js:153`、`production-reconstruction-adapter.js:430`）。

## 4. 目标架构（target authority model）

```
Desktop (Web Core)                 Home Node (Node service, same machine)
  apiConfigs (secret-free)           characters(dto_json)          ── mobile-safe DTO
      │  publish catalog+spec              character_runtime_specs.spec_json
      │  (spec: NO apiKey)                 { provider, model, endpoint, credentialRef, ... }  ── NO secret
      ▼                                      │
  POST /characters/publish                   │ resolve(credentialRef)
                                             ▼
                                   Node-side resolver (active/credential-resolver.js)
                                             │ (allowlist = Node 自己的 characters/spec 集合)
                                             ▼
                                   encrypted Vault (credential-vault.json + key)
                                             │ request-scoped secret
                                             ▼
                                   provider request (mobile turn / understanding tick)
```

要点：
- **spec 不再含 apiKey**，只含 `credentialRef`（= character_id）。
- **读者在请求时**用 Node 侧 resolver 解析 secret（请求作用域，用完即弃，不落库、不缓存）。
- 桌面规范不变：Vault 仍是唯一 authority；Home Node 通过**本机** Vault 解析（同机、同用户数据目录）。

## 6. 数据模型与兼容

- **无 DDL**：`spec_json` 内新增/替换字段即可（`apiKey` → `credentialRef`）。
- **双形状窗口**：过渡期 spec 可能同时存在 `apiKey`（旧）与 `credentialRef`（新）。
  - 读者：**优先** `credentialRef` 解析；仅当无 ref 且存在 `apiKey` 时回退（兼容旧 spec）。
  - 写者：新发布一律**不带** apiKey。
- **可运行判据**：`credentialRef` **或** 过渡期 `apiKey` 之一存在即可运行（避免迁移中出现"角色在手机上突然不可用"）。
- **Vault 绑定**：`credentialRef` = character_id，直接对应当前 Vault binding，无需新绑定（P34.2 已证 14/14 匹配）；若未来某角色无 Vault 绑定，需先补绑定（单独受控步骤）。

## 7. 阶段化迁移计划（**PLAN ONLY，按依赖顺序**）

> 每阶段：Entry / Work / Exit / Rollback。**均未执行。**

**Phase A · Writer stop（停写明文）**
- Entry：设计评审通过。
- Work：W1/W2 落地；新发布的 spec 不含 apiKey、含 credentialRef。
- Exit：新 spec 无 apiKey；旧 spec 仍含 apiKey（未清）。
- Rollback：还原 `mapSpec`；重新发布即可恢复旧形状。

**Phase B · Reader migration（读者迁移，带回退）**
- Entry：A 已灰度（新 spec 带 ref）。
- Work：R1/R2/R3/S1/S2；读者优先经 Node resolver 取 secret，缺 ref 回退 `spec.apiKey`。
- Exit：读者在**有 ref** 时走 Vault；**无 ref** 时仍可用（回退）。
- Rollback：还原读者（回到只读 `spec.apiKey`）。

**Phase C · Fallback removal（去回退）**
- Entry：全量 spec 已带 credentialRef（发布 + 数据迁移完成）。
- Work：删除 `spec.apiKey` 读取回退（C1）。
- Exit：读者**只**认 `credentialRef`；明文回退不可达。
- Rollback：重新引入回退（仅作为应急，需评审）。

**Phase D · Data cleanup（历史明文清理，受控）**
- Entry：A/B/C 落地并验证；具备 `home-node.db` 快照备份。
- Work：对现存 14 行 `spec_json` 做**受控迁移**：读 `apiKey` 建/校验 Vault 绑定（若缺）→ 写 `credentialRef` → 删除 `apiKey` 字段。逐行、事务、可审计。
- Exit：DB 中 `spec_json` 无 `apiKey`；读者全绿。
- Rollback：用备份回滚 DB（保留旧 spec 只读副本直至验证通过）。
- 约束：需 **controlled test + 明确授权**；本阶段不做。

**Phase E · Verification（受控验收）**
- LAN/mobile 角色回合（`mobile-gateway` 路径）成功；
- 后台理解 tick（`understanding-derivation`）成功；
- image route（若在范围）成功；
- `character_runtime_specs` 无明文；DTO 仍无 spec；Recovery 仍 `DEFER`。

**Phase F · Regression**
- fresh install / upgrade smoke（Windows Sandbox 隔离）+ 移动回合 + 理解 tick + 桌面回归。

## 8. 兼容矩阵

| 场景 | 旧写者+旧读者 | 新写者+旧读者 | 旧写者+新读者 | 新写者+新读者 |
| --- | --- | --- | --- | --- |
| phase | 现状 | A 后（旧读者需能读无 apiKey 的 spec） | B 后（新读者带回退） | C 后（终态） |
| 需要 | — | ⚠️ 旧读者要求 apiKey → **A 必须与新读者同批或先 B** | 回退到 apiKey | ✅ 终态 |

> 结论：**排序上 A 与 B 需协同**（先具备"能解析 ref 的读者"再停写明文），否则 A 停写会使旧读者在无回退时不可运行。计划按 A→B 灰度、C 收口。

## 9. 回滚策略

- 保留旧 `spec.apiKey` 直到 Phase C/D 之后；任一阶段失败即还原代码 + 保留/回灌旧 spec。
- Phase D 前对 `home-node.db` 做文件快照（`.yanagent/` 域外临时，验证后清理）。
- 不引入不可逆 schema 变更（本设计无 DDL）→ 回滚无需反向迁移。

## 10. 受控验收 / 测试计划（**NEEDS_CONTROLLED_TEST**）

- 静态：`mapSpec` 输出无 apiKey（白名单断言）；`getCharacterSpec` 无 secret 字段。
- 动态（隔离）：在沙箱/临时数据根内构造"无 apiKey 只有 credentialRef"的 spec，验证 `mobile-gateway` 与 `understanding-derivation` 经 resolver 成功；构造"解析失败"验证 fail-closed。
- 边界：DTO 不含 spec；`/characters` 响应无 spec；Recovery 仍 DEFER。
- 禁止：在**生产**数据上验证（需隔离根）。

## 11. 风险 / 未决（UNDETERMINED）

1. **Home Node 读取 Vault 的权限边界**：Node 服务与桌面同机同用户数据目录，可读 `credential-vault.*`。是否接受"Home Node 进程可解 Vault"是**安全决策**（需评审；替代方案是 Node→桌面 broker）。
2. **allowlist 归属**：resolver CLI 的 allowlist 基于 Active metadata；Home Node 侧应基于自身 `characters`/spec 集合。二者差异需确认（$UNDETERMINED$）。
3. **imageGen 凭据**：`mobile-gateway.js:2024` 提及的 image 凭据是否进入本轮范围未定（需确认 image route 是否在用）。
4. **LAN/mobile 实际使用频率**：P34.2 `activeDevices=0`，但 understanding tick 常驻 → 真实读者活跃度需 controlled test 佐证。
5. **发布失败语义**：现有"发布失败不阻塞桌面、手机报 no-config"（`home-node-bootstrap.js:576`）在去明文后是否仍成立（应成立，因 ref 解析失败=no-config）。
