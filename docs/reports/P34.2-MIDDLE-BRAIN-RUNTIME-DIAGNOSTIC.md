## 0A. 更正（2026-09-26 · 应用户质疑复核）

**本报告 §3.2 曾把 MB endpoint 误读为 `api.openai.com`；实际不是。** 从运行中的安装版通过 WebView2 调试通道只读读取 `IB.middleBrain.getMiddleBrainConfig()` 的真值为：

```text
endpoint = https://api.teamorouter.com/v1/responses   ← 用户的中转站（TeamRouter），不是 api.openai.com
provider = astra ; model = gpt-6-astra ; credentialRef = '' ; apiKeyPresent = true
```

真正根因（TL;DR 的层判定 **C 仍然成立**，只是主机名此前写错）：

```text
api.teamorouter.com  -> DNS 31.13.84.34（Facebook/Meta 网段 = DNS 污染），TCP 443 连接被拒绝
api.teamorouter.cn   -> DNS 36.150.72.74 / 111.2.133.71，TCP 443 OK，POST /v1/responses → HTTP 401（路由存在）
```

即：用户**确实走中转站**，但 MB 的 endpoint 用了中转站的 `.com` 域名；该域名在本机被污染/不可达 → `fetch` 抛异常 → `network`。用户可用的中转域名是 `.cn`。修复见 `docs/reports/P34.2-ASTRA-NETWORK-ROUTING-FIX.md`。

## 0. 结论（TL;DR）

观察到的 error 字符串恰好是 `network`，而 `network` 在代码里**只可能**由传输层 `try/catch` 在 `fetch/_ibApiPost` **抛异常**时产生（`middle-brain-astra.js:178`）。因此：

- config 存在 ✅
- credentialRef/凭据解析成功 ✅（若失败，error 会是 `not_ready`，不是 `network`）
- 请求体构造成功 ✅（否则是 `request`）
- **HTTP 请求本身失败**：**没有拿到任何 HTTP 状态码**（连接抛出）
- → **层 C：network/fetch failure**

运行环境侧的根因：Direct Channel 在 **Tauri（`tauri.localhost`）** 下走**直连 fetch**（不经本地 Bridge），而配置的 Middle Brain endpoint 指向 **`https://api.openai.com/v1/responses`**（默认值）；本机 **`api.openai.com:443` 连接超时**，而其它 provider（deepseek / dashscope / xiaomimimo）**连接正常**。

## 2. 错误字符串 → 失败层映射

代码位置（`middle-brain-astra.js`）：

| error 字符串 | 产生点 | 层 |
| --- | --- | --- |
| `not_ready` | `:150`（readiness）/ `:153`（凭据解析失败） | **A** credential resolver failure |
| `request` | `:157`（`!req \|\| !req.body`：请求体构造失败） | **B** request construction |
| `timeout` | `:178`（`timedOut=true`，AbortController） | **C′** 连接超时 |
| **`network`** | **`:178`（传输抛异常，未超时）** | **C** network/fetch failure |
| `http` | `:180`（`!res \|\| !res.ok`） | **D** provider HTTP error |
| `parse` | `:182`（`!data`，body 非 JSON） | **E** response parsing |
| `empty` | `:186`（解析成功但无 content） | **E** response parsing |
| `error` | `:188` catch-all | — |

### 2.1 本地复现（只读，无真实 API）

脚本对**每种失败注入**真实调用 `middleBrainDirectModelCall`，实测 error 字符串：

```text
PASS  C network (unreachable endpoint, real fetch)  -> error="network"
PASS  D http (401 from provider)                    -> error="http"
PASS  E parse (body not JSON)                       -> error="parse"
PASS  E empty (no content)                          -> error="empty"
PASS  A resolver failure -> not_ready               -> error="not_ready"
PASS  OK (valid wire)                               -> error=true
```

→ 观察到的 `network` **必然**对应「真实 fetch 抛异常」这一路径，与上面的层判定一致。

### 2.2 Tauri vs Browser 的关键差别（为什么是 `network` 而不是 `http`）

`communication.js:125-132 _ibProxyShouldRoute()`：

- **`file:`（浏览器/双击打开）** → `true`：`_ibApiPost` 把请求交给本地 Bridge `/api/llm-proxy` 由服务端发起，绕开 CORS。此时上游不可达会被 Bridge 镜像为**非 2xx 响应** → error 变成 **`http`**。
- **`tauri.localhost`（安装版 Tauri）** → `false`：**直连 fetch**。上游不可达时 `fetch` 直接抛异常 → error 为 **`network`**。

Direct Channel 运行在安装版 Tauri（`http(s)://tauri.localhost`），因此走直连 → 观察到 `network`。**`network` 本身即是「运行在 Tauri 直连路径」的证据。**（复现中若用 Bridge 包装的 `_ibApiPost`，同一不可达 endpoint 得到的是 `http` —— 已实测。）

## 4. 层判定与排除

| 层 | 排除理由 |
| --- | --- |
| **A credential resolver failure** | 若解析失败，`middleBrainModelCall` 在 `:153` 返回 `not_ready`；实测报 `network`，且复现证明 resolver 失败得到 `not_ready`。 |
| **B request construction failure** | 构造失败返回 `request`；实测非此值。 |
| **C network/fetch failure** | ✅ **命中**：`:178` 传输抛异常；`api.openai.com:443` 超时；Tauri 直连无 Bridge；无 HTTP 状态码。 |
| **D provider HTTP error** | 无 HTTP 响应（连接即失败）；若有 4xx/5xx 会是 `http`。 |
| **E response parsing failure** | 从未收到响应体；`parse`/`empty` 均不可能。 |

**判定：C（network/fetch failure）**，根因是 **Middle Brain endpoint（`api.openai.com`）在本机网络不可达**。这是**运行时/配置环境问题**，不是 P34.1 代码缺陷（凭据解析、就绪门、传输映射均按设计工作）。
