## 0A. 更正（2026-09-26 · 应用户质疑复核）

本报告与 P34.2 曾把不可达主机写成 `api.openai.com`；**实际不是**。运行版真值为 `endpoint = https://api.teamorouter.com/v1/responses`（用户的中转站）：`.com` 在本机 DNS 被污染为 `31.13.84.34`（Meta 网段）→ TCP 443 拒绝 → `network`；而 `.cn` 可达且支持 `/v1/responses`（HTTP 401 路由存在）。

- 本报告的**代码修复（复用现有 apiConfig 作为网络路径）依然有效且必要**（它让 MB 能走可达的 provider）。
- 该问题的**直接根因**是 MB endpoint 域名 `.com` 不可达；把它改成 `.cn`（或绑定 `.cn` 的 apiConfig）即可，已实测 `Direct Channel → ok:true`。
- 审计结论「普通 Chat 与 Middle Brain 共用同一 `_ibApiPost`、差异在 endpoint/wire」不受影响。

## 1. 审计：普通 Chat 的 provider routing

| 关注点 | 实现 | 结论 |
| --- | --- | --- |
| proxy 判断 | `assets/js/communication.js:125-132` `_ibProxyShouldRoute()`：仅 `location.protocol === 'file:'` 时返回 true（`o._forceDirect` 可豁免） | **仅 file:// 走 Bridge**；Tauri（`tauri.localhost`）为 `http(s):` → false |
| bridge endpoint | `communication.js:133-137` `_ibProxyBase()` → 默认 `http://127.0.0.1:23115`；服务端处理在 `bridge/routes.js:195-258` `proxyLlm`（`/api/llm-proxy`，通用转发 + SSRF 源校验） | Bridge 只**原样转发**到客户端给的 URL，不换路由 |
| fetch wrapper | `communication.js:147-165` `_ibApiPost()`：file:// → 交 Bridge；否则 `fetch()` 直连 | 普通 Chat 与 Middle Brain 用的是**同一个** `_ibApiPost` |

普通 Chat 调用链：`callApi`（`communication.js:282-283`）→ `_ibWithRuntimeApiCredential` → `_callApiWithRuntimeCredential` → `_ibApiPost(cfg.endpoint, …)`（`:331`，另 `:5844/:6048/:6131`）。

## 2. 对比 Middle Brain

| 关注点 | Middle Brain | 与普通 Chat 的差异 |
| --- | --- | --- |
| 传输 | `assets/js/middle-brain-astra.js:169` `root._ibApiPost(...)` | **相同** |
| endpoint | `cfg.endpoint`（默认 `https://api.openai.com/v1/responses`） | **不同且不可达** |
| wire builder | `AstraAdapter.buildResponsesRequest`（Responses API 专用） | 普通 Chat 走 `AstraAdapter.buildRequest`（按 `providerFormat(provider)` 决定 openai/anthropic/gemini/responses） |
| credential | `resolveRuntimeCredential(cfg)` → `IB.host.credentialResolver` | 相同机制 |

**结论**：传输 seam 相同，差异在 **endpoint + wire 格式**。且运行期实测证明这不是「路由」问题：

```text
node(Bridge 运行时) fetch api.openai.com/v1/responses  -> TIMEOUT
Bridge /api/llm-proxy -> api.openai.com               -> HTTP 502 (上游请求失败: fetch failed)
node / Bridge -> api.deepseek.com                      -> HTTP 401 (可达)
```

即：**本机与本地 Bridge 都无法到达 `api.openai.com`**，任何主机内代理都不能修复。唯一可行方案 = 让 Middle Brain 走**普通 Chat 已在用的、可达的 provider 网络路径**。

## 3. 方案（最小、复用现有 seam）

当 Middle Brain 绑定到一个现有 `apiConfig` 时，**只读复用**该配置的 `provider / endpoint / model` 作为网络路径，并用**同一个** provider-format 感知的 `AstraAdapter.buildRequest` + 同一个 `_ibApiPost` 发送 → 与普通 Chat 走完全相同的可达 seam。未绑定时行为逐位不变。

### 代码改动

| 文件 | 位置 | 改动 |
| --- | --- | --- |
| `assets/js/middle-brain-astra.js` | `:26` `resolveRuntimeCredential` | 凭据绑定 id 改为 `credentialRef \|\| providerConfigId`（仍经 Vault resolver） |
| 同上 | `:47-64` 新增 `_mbProviderPath(cfg)` | 只读 `dbGet('apiConfigs', ref)` 取 `provider/endpoint/model`（`_ibCredentialFreeApiConfigForRuntime` 已剥离密钥）；不可用→null |
| 同上 | `:180-184` `middleBrainModelCall` | 绑定时用 `buildMiddleBrainRequest`（provider-format 感知），否则维持 Responses 路径 |
| 同上 | `:213` | 绑定时用 `parseMiddleBrainResponse`（通用），否则维持 Responses 解析 |
| `assets/js/middle-brain-config-core.js` | `:42, :224, :295` | 新增非密 `providerConfigId` + `normalizeMiddleBrainProviderConfigId` |
| `assets/js/middle-brain-config.js` | `:572-575, :594, :608, :625` | UI 读/写 `providerConfigId`，datalist 复用现有 apiConfigs |
| `InternalBeyond.html` | `:1319-1320` | 新增「网络路径 (复用现有 API 配置)」输入 + datalist |

### 使用方式

Middle Brain 设置卡片 → **网络路径 (复用现有 API 配置)** 填一个现有 apiConfig 的 id（下拉可从现有配置选择）。此后 Direct Channel / judge / integrity 的模型调用都走该配置的可达 endpoint 与正确的 wire 格式；凭据仍从 Vault 解析。留空 = 维持 Middle Brain 自身 Endpoint。

## 6. 诚实说明

- 本机与本地 Bridge 均**无法**到达 `api.openai.com`（TCP 超时 / Bridge 502）。本修复**不**试图让 `api.openai.com` 变可达（在该主机上不可能），而是让 Middle Brain 复用**已在用、可达**的 provider 配置作为网络路径。
- 因此生效前提：用户把一个可达的 apiConfig（例如已配置的 deepseek / dashscope / xiaomimimo）设为 Middle Brain 的「网络路径」或凭据绑定。未绑定时行为与修复前逐位一致。
- 本轮未发起真实 provider 业务请求；验证使用本地 mock provider。

## 7. 结论

- 审计确认普通 Chat 与 Middle Brain 共用同一 `_ibApiPost` seam；差异是 endpoint 与 wire 格式，而非 proxy 路由本身。
- 通过**只读复用现有 apiConfig 作为网络路径**（最小改动、复用现有 provider seam），Middle Brain 请求不再直连不可达 endpoint 失败 `network`，凭据仍经 Vault resolver，secret 不落盘，普通 Chat 不受影响。
