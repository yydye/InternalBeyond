## 1. Mutation types（闭集）

```
like · unlike · comment.create · comment.delete · moment.delete · reply.create
source: user · role_ai · companion · system
decision: allow · deny            （无 DEFER —— 见 §5）
```

不接受自然语言 `mutationType`，不接受自由文本理由；未知词 ⇒ `bad-mutation-type` / `bad-source` ⇒ fail closed。

## 2. Authority（唯一权威）

```
MOMENTS_MUTATION_AUTHORITY_INVARIANT
  任何对**已有** Moment 的修改，都必须先经过 Mutation Authority 的 decision；
  只有 ALLOW 才执行写入。
```

禁止的直达边：`UI event → dbPut`、`AI/model → writer`、`companion → writer`、
`comment/reply executor 自己判断权限`。权威缺席（模块未加载）⇒ **DENY**（fail closed），
绝不退回旧的直写路径。

## 3. Actor identity

`actorId` 必须落在 canonical identity 域：角色 = `apiConfigs.id`（或 archivedConfigs），
用户 = 单一 user principal。**displayName / nickname / 临时 id 不是身份**：
形状校验（非空、无首尾空白、无控制字符、≤200）之外还有 `actorKnown` 事实 ——
角色 id 解析不到配置即 `unknown-actor` ⇒ DENY。

## 4. Executor

decision 在 executor **之前**；executor 只做"把已授权的 mutation 写下去"：
不重新判断身份 / 权限 / policy，不调模型，不重新决策。
executor 失败 ⇒ `executed:true, ok:false`（**不**改写成 DENY）。

## 5. Authority Decision

`allow` / `deny` 两值闭集。**刻意没有 DEFER**：mutation 是即时的幂等动作
（点赞/取消、评论、回复、删除），产品上没有"稍后再改"的语义；引入 DEFER 只会造出
一个没人消费的中间态（Closure 要求"必须证明需要"）。

## 6. Canonical writer

所有 mutation 最终仍只经**唯一**创建/落盘权威：`createMoment` → `_momentsWriteCanonical`
（1 处定义、1 处调用、1 处 `hn.put(m,`）。mutation 不新增 writer、不新增 store、不新增队列。

## 7. Manual mutation（用户）

| 动作 | 路径 | authority |
| --- | --- | --- |
| 点赞 / 取消点赞 | UI → `likeMoment` | `like` / `unlike`（用户主体；作者不能给自己点赞；取消点赞只有用户可做） |
| 评论 | composer → `addMomentComment` | `comment.create`（内容非空、同人同内容去重） |
| 删自己的评论 | UI → `deleteMomentComment` | `comment.delete`（评论作者） |
| 删自己的动态 | UI → `deleteMoment` | `moment.delete`（动态作者） |

## 8. Autonomous mutation（角色 / AI）

| 动作 | 路径 | authority |
| --- | --- | --- |
| AI 点赞 | `_momentsApplyLikes` → `likeMoment` | `like`（选择逻辑仍在既有权重/概率门里；权限只在 authority） |
| AI 评论 | `generateRoleComment` → `addMomentComment` | `comment.create`（必须对动态可见；`aiComment` 与冷却仍是既有前置） |
| AI 回复 | `generateRoleReply` / 回复链 → `addMomentComment` | `reply.create`（被回复评论必须存在） |
| AI 楼主删评 | `_momentsApplyDelComments` → `deleteMomentComment` | `comment.delete`（角色楼主只能删**别人**的评论） |

AI 点赞不撤销（角色 unlike ⇒ `ai-unlike-not-permitted`，caller 保持既有的幂等 no-op 返回）。

## 9. Companion mutation

companion **不写任何东西**（`dbPut` / `dbDelete` 引用 = 0）：它只发事件
`moment_reply`（回复）与 `moment_comment_deleted`（楼主删评），由浏览器 ingest
经 Mutation Authority 裁决后才写：

- `moment_reply` → `reply.create`（actor = 评论作者；角色主体必须对该动态可见）；
- `moment_comment_deleted` → `comment.delete`（actor = 事件里的 `role_id`/`character_id`；
  角色只有作为**楼主**才能删别人的评论）。**不可归属的事件**（缺 actor）⇒ DENY 且 ack。

## 10. Delete rules（冻结）

- `comment.delete`：用户主体可删自己的评论，或删**自己发布的动态**下的任何评论；
  角色主体只能删自己发布动态下**别人**的评论（与既有 `_momentsAuthorCanDelete` 逐字一致）。
- `moment.delete`：用户主体（应用所有者，UI 入口）或动态作者本人；
  其它主体 ⇒ `not-owner` ⇒ DENY。这是对**此前没有检查**的漏洞路径的 fail-closed 收紧，
  现有调用方/测试全部不受影响（它们都是用户主体或作者本人）。

## 11. Frozen contracts

FROZEN：

1. 修改必须经 Mutation Authority（唯一权威，fail closed）
2. mutationType / source / decision / reason 闭集
3. actor 身份必须是 canonical id（displayName / nickname / 临时 id 拒绝）
4. decision 先于 executor；executor 只执行
5. 创建与修改分离：like/comment 绝不进 `runMomentAutonomy`
6. canonical writer 仍然唯一
7. companion / AI 无直接写权限（只能请求 mutation）
8. delete 的所有权规则（§10）

## 12. Deferred（不在本阶段）

- Mutation 的**审计日志**（哪些 mutation 被拒、为什么）目前只进既有观测矩阵，未新增 store；
- Mutation 的**批量/批量撤销**（AI 连环互动）仍按单条 mutation 走同一 authority；
- comment/reply 的**内容安全**（secret / 私密披露）仍是既有 content seam 的职责，
  本阶段不接 `disclosureFacts` / Memory / Middle Brain；
- companion 侧的事件归属如果缺 actor（老版本），会被 fail closed 拒绝；
  后续若需要兼容老 companion，需要单独阶段明确"不可归属事件"的产品语义。
