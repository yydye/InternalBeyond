# InternalBeyond · Release Builder 界面说明（R2）

> 这份文档回答两个问题：**这个界面为什么长这样**，以及**它是不是真的长这样**。
> 第二个问题不靠断言回答 —— 每一张截图都来自真实启动的 `tools\IB-Release-Builder.exe`、
> 真实浏览器引擎渲染的真实窗口，逐张人工看过。

---

## 1. R2 改了什么，没改什么

**改（只有表现层）**

| 之前（R1） | 现在（R2） |
|---|---|
| 主界面渲染 CHECK/BUILD/VERIFY 的逐条 item（期望值 / 实际值 / 证据），是开发者视图 | 主界面只显示人需要知道的：版本、Git、工作区、Release Notes、四个阶段各到哪一步 |
| 没有构建完成后的产物区 | `RELEASE READY` + 文件名 + 大小 + SHA256（可复制）+ 清单/校验文件状态 + 三方对账 + 构建耗时 + 产物目录 |
| 错误是 `BLOCKED` + `[code] message` | 每个已知失败翻译成一句人话 + 「怎么办」+ 原始证据（可展开） |
| 日志在页面下方常驻 | 「详细日志」默认收起，只有条目、真实命令与导出 |
| Release Notes 只能在资源管理器里手工建 md | 「编辑发行说明」在界面内读写 canonical 文件 `docs/release-notes/<版本>.md` |
| 浅色玻璃卡片 + 浅色文字（实测发灰、对比度不足） | 深色玻璃：近黑面板、发丝边框、一处克制的高光、单一强调色、去饱和的四状态色 |
| `hidden` 被 `display:grid` 覆盖，发布弹层在没人打开时就可见 | `[hidden] { display: none !important }`，逐张截图确认过 |

**没改（刻意）**

* 版本权威、U1–U5 校验、`scripts/build-installer.ps1`、清单契约 —— 一行未动；
* 五个阶段的状态机、`lib/plan.js` 的 `canRun` 闸门、`topStatus` —— 一行未动；
* PUBLISH 的逐项确认 + fingerprint 绑定 + 不自动 push/tag/upload —— 一行未动；
* 后端只新增两类端点：只读的 `/api/reveal`（打开 dist / 定位本次日志）和一个受限的
  `/api/notes`（读写 canonical 发行说明，见 §4）。

界面**不决定任何事**：它调用已经存在的阶段、显示已经算出的状态。它不能启动后端会拒绝的阶段。

## 2. 屏幕结构

```

│ IB  InternalBeyond / RELEASE BUILDER   1.0.5 → [1.0.6]  Stable   ● 状态 │
├──────────────────────────────────────────────────────────────────────┤
│ ① 检查 ──→ ② 构建 ──→ ③ 验证 ──→ ④ 封装        ← 一步一句人话，进行中有轻动画 │
│ ────────── 以下动作在 GitHub 上公开，永不自动执行 ──────────              │
│ ○ 发布到 GitHub                                     独立确认            │
├───────────────────────────────────┬──────────────────────────────────┤
│ 发行状态                           │ 需要处理                          │
│ 当前/目标版本 · Git · 工作区        │ 缺少 1.0.6 的 Release Notes       │

│ 构建耗时                           │ 原始证据 ▸                        │
├───────────────────────────────────┴──────────────────────────────────┤
│ RELEASE READY                                         已封装，尚未发布  │
│ InternalBeyond-Setup-1.0.6.exe                                        │
│ 431959f3ac21bb5f…d57a67fbc                            [复制 SHA256]    │
│ 文件大小 / update-stable.json / SHA256SUMS.txt / 三方对账 / 耗时 / 目录 │
│ [打开 dist] [查看日志]                                                │
├──────────────────────────────────────────────────────────────────────┤
│ [构建 Release] [检查] [打开 dist] [编辑发行说明] [预演] [取消] [重置]    │
│ ▸ 详细日志                                                    58 行     │
└──────────────────────────────────────────────────────────────────────┘
```

布局由 `public/app.js` 在三种模式间切换，任何一种模式下都不会出现空面板：

| 模式 | 何时 | 结果 |
|---|---|---|
| `single` | 什么都没有，或还没有产物 | 状态卡占满整行 |
| `paired` | 有问题要处理，但没有产物 | 状态卡与问题并排 |
| `stacked` | 有产物（封装修行中/成功/失败） | 状态卡 → 产物 → 问题，纵向排列 |

产物永远是主角：有问题时也不会把产物挤到看不见的地方。

## 3. 视觉约定

* **深色玻璃**：面板 `rgba(24,31,46,.62)` + `blur(18px)`，发丝边框 `rgba(255,255,255,.085)`，
  顶部一道 `inset 0 1px 0 rgba(255,255,255,.055)` 高光。深度来自分层，不来自投影。
* **文字阶梯**：`#e9eefa` / `#b9c4d8` / `#8b97ae` / `#6b7689` 四级。主文字与面板的对比度
  足够高 —— R1 的问题是浅色文字压在近白玻璃上，实测发灰。
* **一个强调色**：`#6fa8dc`，只用于主按钮、当前阶段、可点击的链接式入口。
* **四个状态色刻意去饱和**：成功 `#74b795`、进行中 `#7ea9dd`、需知 `#d3a868`、失败 `#d98a8a`。
  失败的发行应该读作「看这里」，而不是报警器。
* **动效只有一处**：当前阶段底部一道 1.6 秒循环的扫描线，加上状态点的呼吸；
  总时长与位移都极小，`prefers-reduced-motion` 下全部关闭。
* **不做**：满屏表格、Jenkins 式控制台、Bootstrap 默认按钮、大面积高饱和色。

阶段节点用文字而不是图标表示状态（`✓` 完成、`!` 需读、`×` 失败、`•` 进行中、数字 待运行），
因为一个圆点配颜色的语义要学，而 `✓` 不用。

## 4. Release Notes 编辑器（唯一新增的写入口）

规则不变：`docs/release-notes/<版本>.md` 仍然是 canonical 发行说明文件 ——
`lib/publish.js` 把它交给 `gh release create --notes-file`，`lib/seal.js` 把它的文本折进清单，
`lib/verify.js` 证明清单的 `notes` 仍然等于它。

R2 只增加一个**在界面内编辑这个文件**的入口，它是能加的最窄的写：

| 约束 | 做法 |
|---|---|
| 路径不由调用者决定 | 由 `lib/notes.js` 从(仓库根, 目标版本)推导；请求里没有任何路径字段 |
| 只能碰到那一个文件 | 目标版本必须是 `MAJOR.MINOR.PATCH`，所以 `../../VERSION` 之类的形状直接被拒 |
| 换行 | 浏览器 textarea 会提交 CRLF，服务端一律写 LF —— 否则文件与它自己的规范化形式永久不同（git 会一直报差异） |
| 大小 | 上限 256 KiB |
| 运行中 | 阶段运行期间拒绝写入 |
| 已经钉定之后 | SEAL 或 VERIFY 通过后拒绝写入：那时清单里已经带着这份文本，改它会让那次校验不再成立（而不是静默让它变成假的）。界面在这种情况下禁用按钮并要求先重置重跑 |

保存后界面会**自动重跑一次 CHECK**，因为工作树变了，之前的绿色结论说的是另一棵树。

**它不在发布提交里**：`lib/publish.js` 的 commit 只带 `VERSION` 与 `README.md`，
发行说明文件照旧由人自己提交。这是既有契约，R2 没有改。

## 5. 实测证据（本轮，逐张人工看过）

工具：真实 `IB-Release-Builder.exe` → 真实 `msedge.exe`（headless=new）→ CDP 逐屏截图 +
把渲染后的可见文本一起取回来（只看 DOM 或只看源码都不算数）。

### 5.1 每个状态都被拍下来了

| 截图 | 状态 | 界面上真实出现的文字 |
|---|---|---|
| `01-initial` | 未开始 | `未开始`；四阶段待运行；Release Notes「先填目标版本」 |
| `03-check-done` | 可以继续，有需知项 | 检查节点变 `!` +「4 项需要知道的事」；右侧出现「缺少 1.0.6 的 Release Notes / 怎么办：点「编辑发行说明」…」 |
| `12-notes-saved` | 已填写 | `已创建 docs/release-notes/1.0.6.md`（toast）+ 卡片显示「已填写」 |
| `04-dry-done` | 预演 | `预演完成，没有写任何文件。`；计划原文进「详细日志」 |
| `08-build-running` | 进行中 | `构建进行中…`；构建节点扫描线 +「已 9.2 秒」；其他三个仍待运行 |
| `09-build-done` | RELEASE READY | 四节点 `! ✓ ! ✓`；`构建 InternalBeyond-Setup-1.0.6.exe · 42.3 秒`；`三方对账一致，产物集已封存`；发布入口「已就绪，等待你确认」 |
| `10-publish-modal` | 发布确认 | `v1.0.6 · 文件名 · 50.17 MB（52,608,557 字节）· sha256 431959f3…`；六个动作逐条列出真实命令，不可逆项标「不可逆」；`执行已勾选的动作` 为禁用 |
| `11-publish-armed` | 勾选确认后 | 该按钮变为可用（`executeDisabled: false`）—— 确认链没有被 R2 放松 |

### 5.2 尺寸与缩放

所有组合下 `document.documentElement.scrollWidth == clientWidth`（**无横向溢出**），
底部主操作按钮与「详细日志」始终在首屏内可见（日志是一条固定底栏，不是长滚动的结尾）。

| 视口 | 缩放 | 结果 |
|---|---|---|
| 1280×800 | 100% | 正常：流程条一行四格，状态卡占满整行，按钮与日志都在首屏 |
| 1440×900 | 100% | 正常 |
| 1920×1080 | 100% | 正常（内容居中于 1680px 上限） |
| 1280×800 | 125% | 正常（CSS 视口 1024×640，走短屏规则：卡片更紧凑、日志区更矮） |
| 1440×900 | 125% | 正常 |
| 1920×1080 | 125% | 正常 |

短屏（≤820px 高）会收紧内边距、阶段说明与日志高度；≤700px 时隐去阶段副标题 ——
都是为了不让主操作掉到折叠线以下。

### 5.3 关窗后的残留

每次验证脚本结束时都断言：启动器已退出、`release-builder` 相关的 `node.exe` 子进程数为 **0**。
本轮全部为 0（EXE 用 Windows Job Object 兜底）。

## 6. 如何复现这些截图

视觉验证的驱动脚本**不在仓库里**（它是一次性的取证工具，不是产品的一部分，也不该成为
第六个测试套件）。它做三件事，任何人在本机都可以重做：

1. 以 `IB_RELEASE_NO_BROWSER=1` 启动 `tools\IB-Release-Builder.exe`，从 stdout 读
   `RELEASE-BUILDER-URL`；
2. 以 `--remote-debugging-port` 启动 Edge/Chrome（`--headless=new --window-size=W,H
   --force-device-scale-factor=S`），用 CDP 打开那个 URL 并 `Page.captureScreenshot`；
3. 通过 `/api/run` 驱动真实阶段，在运行中与结束后各截一次。

仓库内的自动化只覆盖**契约**（`tests/test_release_builder_server.js`：端点、令牌、来源、
单阶段闸门、notes 写入边界），不覆盖「好不好看」—— 好不好看只能靠人看截图判断，
这一点没有自动化替代品。

## 7. 已知边界（诚实列出）

* 通道只有 Stable。界面不做 Prerelease 开关，因为冻结的清单契约只认识 Stable ——
  在界面上提供第二个通道就是制造第二份发布真相。
* 「预演」的计划文本是整篇文档，按设计放进「详细日志」而不是主界面。
* 「查看日志」定位的是 `dist/release-<版本>.log`（SEAL 写的发行日志），不是工具自己的实时日志；
  实时日志仍然在「详细日志」里。
* 界面语言是中文，与仓库其余文档一致。
* 构建耗时显示的是 canonical 构建那一条命令的耗时（`facts.buildMs`），
  不含 CHECK / VERIFY / SEAL 自身的时间。
