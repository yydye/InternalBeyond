## 1. GroupTurn runtime state

```js
// communication.js（模块级，runtime-only）
var _gGroupTurnStates = Object.create(null);          // key = group id（与 _chatSendingFor 同一 key 空间）
{
  groupTurnId:  'gturn_…',        // M1 派生值（由触发本轮的 user message id 决定）
  status:       'created' | 'planning' | 'planned' | 'executing' | 'completed' | 'cancelled',
  cancelled:    false,            // cancel 信号（只翻标记）
  cancelReason: '',               // 'user_stop' | …
  plannedCount: 0,                // 本轮计划获得 MemberTurn 的成员数
  startedCount: 0                 // 实际启动过（进入 entry 体）的成员数
}
```

**它只存在于内存**：

- ❌ 不进 DB、不进 `chatMessages.metadata`、不进 prompt、不进 P23；
- ❌ 不新增 store / 表 / 列 / schema 版本；无迁移；无回填；
- ✅ `completed` 只表示"该 GroupTurn 结束"（计划失败 / 空计划也算结束）；是否真的执行过由 `startedCount` 区分；
- ✅ key = group id；同一群同时只有一个回合（`_chatSendingFor` 已保证），新回合覆盖旧条目（自愈），`finally` 统一注销。

### 生命周期与推进点

```
created      _ibGroupTurnBegin(groupId, groupTurnId)          ← userMsg 落库 + _gIdentity 之后
   ↓  _gTurn.status='planning'
planning     validateParticipationInput + planParticipation
   ↓  _gTurn.status='planned'; plannedCount=entries.length
planned      （fail closed / 空计划 / invalid API ⇒ 直接 completed 并 return，不进入 executing）
   ↓  _gTurn.status='executing'
executing    for (const entry of plannedEntries) { if(_gTurn.cancelled) break; … }
   ↓
completed | cancelled      （`_gTurn.cancelled ? 'cancelled' : 'completed'`）
```

## 2. Cancellation semantics（唯一 cancel 信号）

| 事实 | 说明 |
|---|---|
| 信号入口 | `stopStreaming()` → `_ibGroupTurnCancel(activeFriendId,'user_stop')`：**只翻 `cancelled` 标记**，不改状态机 |
| 状态推进 | 由生命周期自己完成（`planned → cancelled`（未进入执行）或 `executing → cancelled`） |
| checkpoint | 每个 entry 开始前：`if(_gTurn.cancelled) break;` |
| 被取消时的保证 | **不启动 provider**、**不产生 assistant 消息**、**不改变 groupOrder**（`order` 由 planner 决定，与取消无关） |
| 已完成成员 | 已落库的 assistant 消息**一律保留**（不撤回、不改写、不补写） |
| 正在执行的成员 | **流式**：仍由既有 `_chatCallStates[chatId].ac.abort()` 中止（同一个 stop 入口）；**非流式**：无法中止（见 §3） |
| 交付层 | 仍走既有 `_ibDeliveryAbort(...)`（P23 唯一入口）；**没有第二套 abort / 第二套队列** |

## 3. Known limitations

1. **非流式成员不可中止**：`callApiChat`/`_callApiChatOnce` 自建 AbortController 仅用于超时，且 `_newCallState(null)` 不入 `_chatCallStates` → 无外部中止入口。因此"停止"在非流式成员上的语义是：**该成员正常跑完并落库，后续成员不再启动**。本阶段刻意**不**扩大共享 API 层（不改 `_callApiChatOnce`，不碰单聊）。
2. **planning/context 窗口内的 cancel**：状态在 `created` 阶段即注册，所以这一窗口的 cancel 也会被记录；但**当前成员**若尚未开始，则与"未启动"同义（不产生任何副作用）。
3. **无 GroupTurn 级"立即中止当前非流式请求"**：需要新增请求登记表（新的 authority），属后续阶段。
4. **budget capability 已存在于 planner**（M3.3.2：`maxResponders` + `budget-limit`，contract v2），
   但**生产取值来源与默认 cap 尚未启用** —— 生产 adapter 不传 `maxResponders`，因此群聊当前默认仍是
   **unlimited**（所有 eligible 成员参与）；本文件不声称"群聊现在默认限制人数"。
5. **recent-speaker 已接线但不生效（M3.3.3.3）**：planning 阶段现在会派生 `recentSpeakerIds` 并交给
   planner，但因为生产仍 unlimited，**当前不会**裁剪 / 重排任何参与者（用户可见行为不变）。
   派生窗口是临时 v1 adapter policy（`GROUP_RECENT_SPEAKER_WINDOW = 2` MemberTurn），
   归属未来的 Group Participation Policy。
   仍未实现：recent-speaker **suppression 生效** / explicit targeting / mention metadata / DEFER / INTERJECT / Group Brain。

## 6. Planning-time 快照与生命周期（M3.3.3.3）

```
created   _ibGroupTurnBegin(...)            ← userMsg 落库之后
   ↓
planning  【ONE CANONICAL SNAPSHOT】_gSealTs + gMsgs（每个 GroupTurn 只读一次 chatMessages/byFriend）
          → deriveRecentSpeakerIds(gMsgs, …)   ← 恰好 1 次
          → planParticipation({ …, recentSpeakerIds })   ← 恰好 1 次
   ↓
planned → executing → completed | cancelled
```

- 快照**只**发生在 planning，且 `gMsgs` 之后被 prompt history 复用（同一份，不二次读库）；
- 本轮成员回复在快照之后产生 ⇒ 不可能回流进 recent（本轮新回复只经 `roundExtras` 传给后续成员）；
- cancel 仍属 execution：不重新派生、不重新规划（`if(_gTurn.cancelled)break;` 仍是唯一 checkpoint）；
- 派生失败 ⇒ planning fail closed（与 planner 失败同一路径）。

## 4. 边界（不改的东西）

- `planParticipation` 仍是**唯一**参与权威；`groupOrder = entry.order`；plan runtime-only；fail closed 不回退；
- **silence is not message**：取消不写 DB、不建系统消息、不为被取消成员补行；
- **P23 五个核心模块零修改**（delivery-planner / multimodal-delivery-policy / delivery-sequence-core / delivery-runtime / voice-message-core）；
- **单聊路径零修改**（`stopStreaming` 的既有语义逐字保留；新信号只作用于群 id 的 GroupTurn 状态，若无该状态则 no-op）；
- `workspace.js` / `social.js` / Middle Brain / Memory 未触碰。
