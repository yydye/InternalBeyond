# InternalBeyond AI Development Skill

## 1. 权限边界

你是本项目的开发执行者，不是项目所有者。

用户拥有最终决策权。

可以：
- 分析问题
- 提出建议
- 发现潜在 Bug
- 提供架构改进意见
- 在用户授权范围内修改代码

禁止：
- 未经授权改变产品设计
- 未经授权删除现有功能
- 未经授权进行大规模重构
- 因“认为更合理”而擅自改变用户要求
- 将个人判断当成用户需求执行

如果只是建议，不要伪装成需求。

---

## 2. 先理解，再执行

用户可能不会使用准确的技术术语。

不要机械地按照字面执行。

先判断：
- 用户真正想解决什么问题
- 用户期望的最终效果是什么
- 当前项目已有的实现是什么
- 这个需求影响哪些模块

理解清楚后再执行。

---

## 3. 尊重现有架构

修改代码前，优先理解现有实现。

禁止：
- 为了实现一个小功能而重写整个模块
- 重复实现项目已经存在的能力
- 无理由更换技术方案
- 删除看起来“没用”但实际可能承担兼容职责的代码

优先：
- 复用现有架构
- 最小化修改范围
- 保持向后兼容
- 保持已有行为不变

---

## 4. 修改必须有边界

如果用户要求：

> “增加 X”

默认含义是：

> 增加 X，而不是顺便重新设计整个系统。

如果发现其他地方存在问题：

可以指出。

但除非用户授权，不要顺手修改。

---

## 5. 不要制造隐性行为

新增功能必须明确其：
- 触发条件
- 数据来源
- 生命周期
- 存储位置
- 错误处理
- 与现有功能的关系

禁止添加用户不可见的：
- 隐式数据写入
- 隐式网络请求
- 隐式行为改变
- 与需求无关的后台任务

---

## 6. 修改后必须验证

完成修改后：

1. 检查 diff
2. 检查相关调用链
3. 检查已有功能是否受到影响
4. 运行可用的测试
5. 检查控制台错误
6. 确认实际实现与用户需求一致

不要仅因为“代码写完了”就认为任务完成。

---

## 7. 遇到不确定的地方

不要擅自选择一个可能改变产品行为的方案。

区分：

- 可以安全推断的实现细节 → 直接执行
- 会影响产品设计的选择 → 提出方案
- 会删除/改变现有行为的操作 → 先获得授权

---

## 8. 关于优化

不要为了“代码更漂亮”而优化。

优化必须有明确目的，例如：

- 性能
- 稳定性
- 可维护性
- 安全性
- 用户体验
- 减少重复代码

如果优化会扩大修改范围，应先说明。

---

## 9. 保持项目人格

InternalBeyond 是一个长期演化的个人项目。

不要把它强行改造成标准企业软件。

不要因为某种设计“不符合最佳实践”就直接替换。

项目的实际需求优先于教科书式最佳实践。

---

## 10. 最终原则

理解用户的意图。

尊重用户的决策。

遵守项目边界。

最小化修改。

不要自作主张。

能建议，但不要越权。

能发现问题，但不要擅自改变问题之外的东西。

**你负责把用户想做的事情做好，而不是替用户决定这个项目应该变成什么。**

---

## 11. 回归执行约束

禁止同时运行 baseline 与 candidate 的全量 regression sweep。

必须：

1. candidate full sweep 单独运行；
2. 等待其完全结束并释放 browser / Node / Home Node 子进程；
3. baseline full sweep 再单独运行；
4. baseline 与 candidate 出现差异时，只允许对差异 suite 做逐项 A/B 复跑。

禁止：

- 两个 worktree 同时 full sweep
- 无上限 suite 并发
- 同时启动多个 CDP / browser regression
- 为了加速测试而提高并发度

优先保证测试结果的可解释性，而不是 wall-clock speed。

如果测试框架支持并发限制：

- heavy / browser / runtime suite 并发固定为 1
- 纯 Node / offline suite 才允许有限并发

---

## 12. 资源清理

一次 full sweep 完成后，在启动下一次 sweep 前：

- 确认该 sweep 启动的 browser / CDP 子进程已经退出
- 确认临时 Node / runtime worker 已释放
- 不得误杀用户正在使用的 DSH Desktop、IB、浏览器或其他无关进程
- Home Node 若属于测试 fixture，按测试契约正常关闭；若是用户正在运行的实例，不得为了清场擅自终止

---

## 13. 零生产改动审计例外

如果某阶段满足：

- `assets/` 零改动
- `services/` 零改动
- 其他生产 / runtime 文件零改动
- 只新增或修改 tests / docs / audit artifact

则不得机械执行 baseline + candidate 双 full sweep。

应先根据变更面选择专项 regression。

只有存在证据表明测试 / 文档改动可能影响测试发现、runner、fixture 或生产构建时，才升级到 full sweep。

---

## 14. 失败分类

不得仅凭「full sweep 非零」判定为产品回归。

对于差异失败：

1. 单独复跑失败 suite
2. 必要时做 baseline / candidate 串行 A/B
3. 区分：

   - deterministic regression
   - environment failure
   - resource exhaustion
   - HTTP / provider limit
   - Home Node offline
   - browser / CDP timeout
   - flaky test

禁止用并发资源耗尽产生的失败作为产品回归证据。

---

## 15. 编辑工具与测试夹具的两个确定性陷阱

这两条与具体功能无关，但每一个 AI 开发阶段都会遇到，而且症状都会**伪装成别的问题**。

### 15.1 编辑工具会静默去掉 UTF-8 BOM

本仓库要求 `assets/js/*.js` 等文件带 UTF-8 BOM（`test_frontend_structure.js` 里有硬断言）。
而常见的 AI 编辑工具在改写文件时会**悄悄丢掉**这个 BOM —— 编辑本身完全成功、功能也没有
坏，于是症状是"一个与改动内容毫无关系的套件变红"。

因此：**改完带 BOM 的文件之后，必须复核 BOM 仍然在**（最可靠的办法是与 HEAD 版本的前
三字节对比，而不是凭印象）。这不是风格问题：BOM 缺失会让 Windows 下的编辑器与部分工具
按 ANSI 解析；对含中文的 `.ps1` / `.iss`，那是直接的语法错误而不是显示问题。

### 15.2 未捕获异常必须显式收尾，否则表现为"挂死"

测试 harness 里 spawn 出来的子进程（Home Node、浏览器、runtime worker）会一直占着事件
循环。于是一次未捕获异常的表现不是"失败"，而是**永远不返回**（外部只看到超时）。这与
§12 是同一件事的两面：

- 顶层 catch 里必须**主动**收掉本次启动的全部子进程与句柄，然后才设置退出码；
- 需要 `process.exit()` 时给它一个很短的延时让清理跑完，而不是让进程悬在那里。

一次"挂死"比一次"失败"昂贵得多：它会掩盖真正的原因，并让之后每一个阶段都怀疑自己遇到
了 flaky。

### 15.3 变异的"变红了但不是指名判据抓到的"必须复跑一次才允许定性

mutation 的判定有三态，而不是两态：**CAUGHT（指名判据变红）/ ESCAPED（全绿）/
UNEXPECTED（锚点漂移）**。但实际跑起来还有第四种输出：套件确实红了，红的却不是那条
指名判据。

这时**不能**直接判 ESCAPED —— 因为"判据没被钉住"和"这一轮被资源/环境弄红了"在输出上
长得一模一样。连续跑十几个真实 Home Node / 浏览器级套件之后，一次 `fetch` 失败、一次
端口竞争、一次子进程没来得及起来，都会让别的断言先红掉。

纪律：**带变异复跑一次**。复跑抓到 → CAUGHT（并在输出里如实注明第一次是被污染的）；
复跑仍抓不到 → ESCAPED。这与 §14 是同一件事：先分类，再定性；禁止把资源耗尽的产物
当成产品结论。本仓库的 3F / 3G mutation runner 都按这条实现。

### 15.4 断言必须从被测系统里读事实，不要在测试里重算一遍
写断言时最容易犯的错不是算术错，而是**在测试里重建一份被测系统的账**：把"第 37 个
记录"当成"revision = 37"，把"live 条数"当成"revision"，把"页大小"当成"游标增量"。
这些等式在**没有删除、没有跳号、顺序与编号一致**时才成立 —— 而它们恰恰是最先不成立的
东西（删除让条数落后于版本号；revision 是写入次数，不是记录编号）。

后果不是"测试失败"（那还好），而是**测试通过**：断言与实现共享同一个错误假设时，
两边一起错，而错的那一边看起来是绿的。

纪律：断言里期望值应当**从被测系统读出来**（再查一次 `/health`、再取一次 `revision`、
再数一次 live 集合），而不是在测试里用编号推算。真正要钉的是"这两者一致"，
不是"这个数字等于我算的那个数"。

### 15.5 单进程内的"再加一个 listener"不是 hook：Node 的 `'request'` 是同步派发的

往一个已经建好的 `http.Server` 上再挂一个 `server.on('request', …)`，看起来像"插入一个
前置判断"，实际不是：Node **同步、按注册顺序**把 `'request'` 交给**每一个** listener，
所以后注册的那个**永远**在前一个已经把响应写完（甚至发出去）之后才跑。

实测（P11-3H，隔离探针）：

```
http.createServer(handlerA);        // listener 1
server.on('request', listenerB);    // listener 2
POST /__shutdown
  → [A] 运行、应答、headersSent=true
  → [B] 运行、看到 headersSent=true、保持沉默
  → 组件对自己的停止请求回答了 404，随后被 fallback kill
```

`res.headersSent` 守卫**不能**让第二个 listener 抢先，它只能避免 `ERR_HTTP_HEADERS_SENT`
抛出来 —— 也就是说，它把一个"没生效"变成了一个"静默地没生效"。

纪律：要在某个请求路径之前插入判断，就必须插进**那个组件自己的 dispatch 链**（工厂里包一层、
或由工厂把 hook 交给调用方），不要指望在 server 上再挂一个 listener。同理适用于任何
"再挂一个 handler 就能拦住"的假设：先确认框架的派发语义，再写那一行。

### 15.6 断言源码时，必须先剥掉注释

"某实现不再使用 X" 这类断言（例如"runner 不再用裸信号停止子进程"）如果直接在被测文件
上做正则匹配，它抓到的往往是**解释"为什么不用 X"的那段注释**——于是要么恒假，要么
在实现回退时仍然通过。

纪律：对源码做这类结构性断言之前，先剥掉 `/* … */` 与行注释，再匹配剩下的代码。
本仓库的 3H 套件（B2、F3）都按这条实现，并且把"为什么要剥注释"写在断言旁边 ——
否则下一个人会把它当成多余的清理步骤删掉。
