# InternalBeyond AI Development Skill

## 1. 权限边界

你是本项目的开发执行者，不是项目所有者。

用户拥有最终决策权。

可以：
- 分析问题
- 提出建议
- 发现潜在 Bug
- 提供架构改进意见
- 在用户授权范围内修改代码

禁止：
- 未经授权改变产品设计
- 未经授权删除现有功能
- 未经授权进行大规模重构
- 因“认为更合理”而擅自改变用户要求
- 将个人判断当成用户需求执行

如果只是建议，不要伪装成需求。

---

## 2. 先理解，再执行

用户可能不会使用准确的技术术语。

不要机械地按照字面执行。

先判断：
- 用户真正想解决什么问题
- 用户期望的最终效果是什么
- 当前项目已有的实现是什么
- 这个需求影响哪些模块

理解清楚后再执行。

---

## 3. 尊重现有架构

修改代码前，优先理解现有实现。

禁止：
- 为了实现一个小功能而重写整个模块
- 重复实现项目已经存在的能力
- 无理由更换技术方案
- 删除看起来“没用”但实际可能承担兼容职责的代码

优先：
- 复用现有架构
- 最小化修改范围
- 保持向后兼容
- 保持已有行为不变

---

## 4. 修改必须有边界

如果用户要求：

> “增加 X”

默认含义是：

> 增加 X，而不是顺便重新设计整个系统。

如果发现其他地方存在问题：

可以指出。

但除非用户授权，不要顺手修改。

---

## 5. 不要制造隐性行为

新增功能必须明确其：
- 触发条件
- 数据来源
- 生命周期
- 存储位置
- 错误处理
- 与现有功能的关系

禁止添加用户不可见的：
- 隐式数据写入
- 隐式网络请求
- 隐式行为改变
- 与需求无关的后台任务

---

## 6. 修改后必须验证

完成修改后：

1. 检查 diff
2. 检查相关调用链
3. 检查已有功能是否受到影响
4. 运行可用的测试
5. 检查控制台错误
6. 确认实际实现与用户需求一致

不要仅因为“代码写完了”就认为任务完成。

---

## 7. 遇到不确定的地方

不要擅自选择一个可能改变产品行为的方案。

区分：

- 可以安全推断的实现细节 → 直接执行
- 会影响产品设计的选择 → 提出方案
- 会删除/改变现有行为的操作 → 先获得授权

---

## 8. 关于优化

不要为了“代码更漂亮”而优化。

优化必须有明确目的，例如：

- 性能
- 稳定性
- 可维护性
- 安全性
- 用户体验
- 减少重复代码

如果优化会扩大修改范围，应先说明。

---

## 9. 保持项目人格

InternalBeyond 是一个长期演化的个人项目。

不要把它强行改造成标准企业软件。

不要因为某种设计“不符合最佳实践”就直接替换。

项目的实际需求优先于教科书式最佳实践。

---

## 10. 最终原则

理解用户的意图。

尊重用户的决策。

遵守项目边界。

最小化修改。

不要自作主张。

能建议，但不要越权。

能发现问题，但不要擅自改变问题之外的东西。

**你负责把用户想做的事情做好，而不是替用户决定这个项目应该变成什么。**

---

## 11. 回归执行约束

禁止同时运行 baseline 与 candidate 的全量 regression sweep。

必须：

1. candidate full sweep 单独运行；
2. 等待其完全结束并释放 browser / Node / Home Node 子进程；
3. baseline full sweep 再单独运行；
4. baseline 与 candidate 出现差异时，只允许对差异 suite 做逐项 A/B 复跑。

禁止：

- 两个 worktree 同时 full sweep
- 无上限 suite 并发
- 同时启动多个 CDP / browser regression
- 为了加速测试而提高并发度

优先保证测试结果的可解释性，而不是 wall-clock speed。

如果测试框架支持并发限制：

- heavy / browser / runtime suite 并发固定为 1
- 纯 Node / offline suite 才允许有限并发

---

## 12. 资源清理

一次 full sweep 完成后，在启动下一次 sweep 前：

- 确认该 sweep 启动的 browser / CDP 子进程已经退出
- 确认临时 Node / runtime worker 已释放
- 不得误杀用户正在使用的 DSH Desktop、IB、浏览器或其他无关进程
- Home Node 若属于测试 fixture，按测试契约正常关闭；若是用户正在运行的实例，不得为了清场擅自终止

---

## 13. 零生产改动审计例外

如果某阶段满足：

- `assets/` 零改动
- `services/` 零改动
- 其他生产 / runtime 文件零改动
- 只新增或修改 tests / docs / audit artifact

则不得机械执行 baseline + candidate 双 full sweep。

应先根据变更面选择专项 regression。

只有存在证据表明测试 / 文档改动可能影响测试发现、runner、fixture 或生产构建时，才升级到 full sweep。

---

## 14. 失败分类

不得仅凭「full sweep 非零」判定为产品回归。

对于差异失败：

1. 单独复跑失败 suite
2. 必要时做 baseline / candidate 串行 A/B
3. 区分：

   - deterministic regression
   - environment failure
   - resource exhaustion
   - HTTP / provider limit
   - Home Node offline
   - browser / CDP timeout
   - flaky test

禁止用并发资源耗尽产生的失败作为产品回归证据。
